## Highest-priority obstacle and change justification

### Verified problem

The inbox owner-beta setup displayed six equally prominent fields: Gmail query, maximum messages, Sheet URL, tab, calendar ID, and access key. Four already had safe defaults. The direct screenshot and owner report show that presenting them as required decisions made the path unclear before the first scan.

### Why this was highest leverage

Unlike speculative professor scope, this was direct observed product feedback on an implemented workflow. It blocked owner activation of a real connected workflow and contradicted the product's documented default-first principle.

### Expected outcome and metric

- Reduce visible setup boxes from six to two.
- Preserve 100% of required consent and human-review controls.
- For the next observed owner test: reach the scan action without asking what belongs in the query, message-count, tab, or calendar fields.
- Later activation metric: setup-to-first-scan completion and setup help requests.

### Alternatives considered

1. No change: rejected because a verified activation problem would remain.
2. Rewrite labels while retaining six boxes: lower risk, but it would still make safe defaults look like decisions.
3. Automatically create a spreadsheet and remove that input: potentially lower effort, but it would add a new Google write and destination lifecycle that was not needed to resolve today's evidence.
4. Remove the access key or consent: rejected because that would weaken the owner-beta security boundary.

### Validation needed

- Automated proof that advanced fields are absent from the default render.
- Complete local quality gate and route contracts.
- One observed owner retry: no clarification needed before entering the Sheet link and private owner key.
- Keep if the owner reaches scan setup unaided; revise if either remaining field is still unclear.
